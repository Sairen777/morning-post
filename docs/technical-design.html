Morning Post · Technical Design Documentation

Current architecture, self-host posture, security, and scalability review

This document records the repository architecture as reviewed on 2026-07-30 and the supported v1 deployment posture of one independently operated single-owner self-host. Current implementation coverage includes name-only first-run owner setup, passwordless continuation with compatibility for existing password-backed owners, the Bun 1.3.14/Hono API, SolidStart web UI, Bun-native SQLite persistence and atomic rate limiting, stale-recovery-first scheduling for zero or one owner, the connector-neutral story pipeline, Telegram and Substack connectors, the TwexAPI-backed X connector, and the OpenAI-compatible analysis and summarization boundary.

Primary assets
Credentials, sessions, messages, key material

Telegram session strings, imported Substack session-cookie values, Morning Post session cookies, owner prompts and interest rules, message/post text and media, story analyses, summaries, feedback, and digest history. The X connector stores envelope-encrypted TwexAPI credentials — API key, X auth_token, and the complete X Cookie header, plus an optional XChat PIN and list query — and persists normalized X posts and chat messages with visible metrics or reactions. The encrypted X session material is account-equivalent custody and is forwarded to the configured TwexAPI provider over HTTPS.

Main risk
Trusted self-hosted custodian and X session-material holder

The operator-run server must decrypt connector credentials, protect the stored X auth token and full Cookie header as account-equivalent session material, and may send plaintext content to the configured summarizer while the primary owner is offline. The third-party TwexAPI provider receives the X session material, adding provider terms, breakage, and account-restriction risk.

Executive summary

The current architecture is a layered, single-owner self-host with explicit security and operating boundaries.

What is strong
  • Repository functions consistently accept userId and scope reads/writes to ownership.
  • First-run setup atomically creates exactly one owner from the digest display name and starts a session; subsequent passwordless continuation requires no credential, while upgraded owners with a retained password hash still verify it.
  • Session tokens are random 256-bit values; only SHA-256 token hashes are stored.
  • Connector credentials use envelope encryption with AES-256-GCM and owner-bound AAD.
  • Item analyses, stories, delivered story cards, feedback, and digests use database uniqueness constraints and idempotent upserts.
  • Service seams are explicit: connectors fetch and normalize, story intelligence analyzes/resolves/classifies, summarizers write story points, and repositories persist.
Operational boundaries and limits
  • Bun processes inherit the operating-system privileges of their account; filesystem, environment, network, subprocess, and native-module boundaries must therefore be enforced by deployment isolation and application code.
  • Rate limiting uses atomic SQLite rate_limit_buckets upserts. Direct socket addresses are trusted by default; forwarding headers are considered only when TRUSTED_PROXY_COUNT explicitly describes the proxy chain.
  • Each digest tick recovers stale runs before selecting the earliest user row as the owner, then processes zero or one owner. Croner protect: true skips overlapping callbacks in the supported single API process; there is no scheduler lease or runtime leader election.
  • Story analysis and summarization are provider boundaries with deployment-wide text and vision endpoints, deterministic text/item/image caps, and run-local media-description fallback behavior.
  • Connector media remain local, but per-connector quotas and a weekly TTL sweep bound retention on a single host.
  • The X connector retains normalized raw posts and chat messages in the SQLite content cache — including messages that later disappear on X — until an account-identity reset deletes them: disconnect and same-account reconnect preserve everything, and only a reconnect to a changed or unknown identity clears the cache and normalized items. Only uncovered time gaps call the TwexAPI provider, and future configurable retention must cascade through raw and derived records rather than relying on X-side disappearance.
Important corrections
  • No current digest-run IDOR was confirmed: GET /digests/runs/:id first loads the run with findDigestRunForUser(database, id, context.var.userId), then lists feed rows for the owned run.
  • listDigestRunFeedsForRun(database, runId) is still a fragile repository helper because it is not self-scoped; pass userId if another caller is added.
  • upsertDigestForPeriod is already atomic: it uses insert(...).onConflictDoUpdate(...).returning(). There is no current check-then-insert race in digest upsert.
Security decision: Self-hosting changes who holds custody; it does not make Morning Post zero-knowledge. The primary owner controls the instance, SQLite database file, media, tokens, and encrypted X connector credentials, but scheduled work still requires local decryption. Plaintext exists in the process after decryption and crosses the operator-controlled host boundary when a remote summarizer is configured. Credential encryption, owner authentication, internal userId ownership scoping, atomic database-backed rate limits, protected backups, filesystem access controls, and host hardening remain defense-in-depth; Morning Post v1 does not introduce a shared service, database, or centralized credential vault.
System context

Morning Post v1 supports independent, single-owner self-hosts; the code retains user-scoped boundaries.

Morning Post is open-source software deployed and operated independently: each supported v1 instance has one primary owner and its own API process, local SQLite database file, media directories, connector credentials, and summarizer configuration. There is no shared Morning Post control plane, hosted database, or project-operated credential store. The account surface remains name-only setup and deterministic owner continuation; public registration and email login are absent.

Trust boundaries

  • Deployment boundary: one primary owner operates one independent instance and controls its database, media, connector tokens, encryption configuration, backups, and host. Self-hosting removes project-wide custody, not the need for least privilege, TLS where traffic leaves loopback, protected backups, patching, and host isolation.
  • Browser → API: cookie-authenticated requests. Origin guard middleware on unsafe requests validates Origin or Referer against the configured ALLOWED_ORIGINS. Security headers include HSTS, frame denial (DENY), and nosniff. Body size is limited by MAX_REQUEST_BODY_BYTES. Even with one primary owner, authentication and userId filters contain stale-session, route, and persistence mistakes and remain future-safe boundaries.
  • API → SQLite file: Bun 1.3.14 bun:sqlite through Drizzle's bun-sqlite driver persists sensitive metadata and encrypted credentials. DATABASE_PATH resolves by explicit override, then environment, then ./data/morning-post.sqlite. The connection uses strict binding mode, foreign_keys=ON, WAL, a 5-second busy timeout, and synchronous=FULL. The database and its WAL/SHM companions must remain on a local filesystem, not NFS or SMB, with directory and files readable and writable only by the dedicated process identity.
  • API → Telegram: Telegram session credentials are full-account bearer tokens. Server custody is unavoidable for scheduled digests.
  • API → Substack: users explicitly import substack.sid and may also provide connect.sid when their browser has it; Morning Post never accepts a Substack password or raw cookie header. Account-subscription discovery and paid/full post retrieval send only the provided session cookies to the fixed https://substack.com origin. Manual publication validation fetches public archives without cookies through the IP-pinned HTTPS boundary. The integration replays an unsupported browser session and may conflict with Substack terms; the UI discloses that risk before connection.
  • API → TwexAPI provider → X: the connector is HTTP-only: it calls the configured TwexAPI base URL (explicit server override, then TWEXAPI_BASE_URL, then https://api.twexapi.io) with the API key as a bearer token. The X auth_token is sent only to GET /twitter/{auth_token}/user_info; XChat discovery and DM history receive the full Cookie header, never the bare auth token. No browser, Chromium profile, installed Chrome, or X login is involved, and no X password or 2FA code is ever accepted. The stored credentials are account-equivalent session material: the provider sees the auth token and cookie, so the provider is part of the trust boundary and the same credential hygiene (least privilege, encrypted backups, host isolation) applies.
  • API → summarizer: normalized message/post plaintext and selected media remain visible to the local process. A loopback summarizer stays within the operator-controlled host; enabling a remote endpoint sends that plaintext across a separately configured provider boundary. Self-hosting therefore does not remove the privacy decision represented by ALLOW_REMOTE_SUMMARIZATION.
  • API → filesystem: media are local files with feed-isolated paths, per-connector quota (MEDIA_QUOTA_BYTES), and a weekly TTL sweep (MEDIA_TTL_MS). Bun's Node-compatible filesystem APIs operate with the process account's privileges rather than runtime permission flags. Deployment ownership and filesystem ACLs should restrict the process to every connector-specific media directory from CONNECTORS_MEDIA_DIR (telegram_media, substack_media, youtube_media, reddit_media, x_media, rss_media) plus the shared/legacy ./media; application path validation, feed isolation, quotas, eviction, and TTL traversal remain the in-process boundaries.

X integration — TwexAPI provider connector

Implemented over the TwexAPI HTTP provider; third-party and unsupported by X. Morning Post connects to X through the TwexAPI API with operator-supplied credentials — a TwexAPI API key, the X auth_token, and the complete X Cookie header — over HTTPS. There is no browser automation, profile directory, or manual login; the application never accepts an X password or 2FA code. TwexAPI is an independent, unofficial X data provider: endpoints, schema, and availability can change, and its terms may conflict with X's. Operators assume the account and policy risk of sharing session material with the provider. The official X API and X OAuth 2.0 surfaces remain the preferred fallback where their capabilities fit.

Connection request and validation
The connection request is exactly { apiKey, authToken, cookie, pin?, listQuery? } to POST /connectors/x/session. The API key and auth token are separate secrets; the cookie is the complete X Cookie header value and must contain a nonempty auth_token pair equal to the separately provided authToken plus a nonempty ct0 pair. Duplicate auth_token or ct0 pairs and control characters are rejected without echoing either value. The XChat PIN is optional, is sent only with DM-history requests, and defaults to 1234 there; conversation discovery does not use it. A blank list query derives from the authenticated username returned by user info. The web form always supports connect and reconnect, renders every secret field as a password input, sends the exact request, clears the secret fields on success, and retains the nonsecret list-search query.
Provider endpoints and boundaries
User info uses GET /twitter/{auth_token}/user_info with the API key as a bearer token and returns the canonical X user ID and username that identify the connected account. List discovery is search-based (POST /twitter/list/search) because TwexAPI provides no owned-lists lookup, and list tweets paginate through POST /twitter/list/tweets/page. XChat group discovery uses POST /v3/twitter/conversations and history uses POST /v3/twitter/dm-history; both XChat bodies receive the full cookie (never the bare auth token), and DM history also carries the PIN. Only group conversations become feeds; direct chats are excluded. No credentials are bundled with Morning Post, and no live X login ever occurs.
Discovery: list and group-only chat feeds
Discovery emits only x:list:<positive-numeric-id> and group-only x:chat:<conversation-id> identifiers. Group labels include the participant count and the conversation ID, e.g. Group (5 participants) - <id>. Direct conversations are never offered as feeds, so a direct-DM external ID can never be cataloged, and conversation IDs remain opaque: the connector does not infer group-ness from the ID. Feed discovery and subscription use the generic GET /sources/:sourceId/available-feeds and POST /sources/:sourceId/feeds routes shared with Telegram; source disconnect is the generic credential removal.
Discovery authorization catalog and catalog-bound subscription
Successful X discovery is revision-revalidated and then atomically replaces the source's whole catalog in one immediate transaction: x_discovered_feeds (migration 0004) holds exactly the Lists and group chats the provider returned for that credential revision, in plaintext (external_id, server-canonical name/kind), unique on (source_id, credential_revision, external_id), and cascade-deleted with the source. Subscription (POST /sources/:sourceId/feeds) makes no TwexAPI call: inside the same immediate transaction that locks the source row it requires an exact current-revision catalog entry, substitutes the catalog's canonical name/kind for any client-supplied metadata, rejects malformed external IDs as validation errors, and rejects uncataloged targets — including direct-DM conversations — with a conflict instructing fresh discovery. Revalidation and subscription use a connected-revision guard that deliberately ignores enabled: connected-but-disabled sources stay discoverable and subscribable, because enabled gates only digest inclusion and ingestion, not authorization. An active-feed cap mirrors the connector's 250-per-batch limit: a subscription that would leave more than 250 active (not soft-deleted) feeds is rejected inside the same transaction.
Pagination through the requested lower bound
List-tweet retrieval pages through the provider until an item older than the inclusive requested from bound is seen or the provider is exhausted; every successful page is durably recorded before the next provider request — and before an abort racing the response is propagated — so a failed page or an interruption leaves the items and the next cursor behind and a retry resumes the range from the saved cursor instead of re-fetching page 1. Each distinct successful page is durably recorded before its cursor is followed, with its cursor appended to a durable bounded history (newest 500 per range); a repeated or cyclic cursor is detected inside the same atomic write that saves the page — including cycles across process or connector restarts — and terminally blocks the range with repeated_cursor, while a claimed next page without a resume cursor saves the page and terminally blocks the range with missing_cursor. A terminally blocked range fails locally before any further provider request on later overlapping runs until the operator disconnects and reconnects X; the identity-less reconnect resets the X cache, subscriptions, and progress. DM-history retrieval sends all: true with count: 200 and makes at most one DM-history request per feed per connector operation: an all-mode response that still claims more history is persisted and then raised as a resumable local error, so the next operation resumes once with the saved cursor as before. A chat range is capped at two DM-history requests in total — after a second incomplete all-mode response, later overlapping runs fail locally before any DM-history request, and the retained progress intentionally blocks repurchasing until the operator disconnects and reconnects X; the identity-less reconnect resets the X cache, subscriptions, and progress. A page beyond the safety limit fails the fetch instead of advancing coverage. A successful empty fetch still establishes coverage. Read ordering is stable by date then external ID.
SQLite raw-item cache and coverage ranges
Raw X posts and chat messages are persisted per source and feed in x_content_cache_items, with inclusive covered ranges in x_content_cache_ranges (migration 0002, cascade-deleted with their source). Every valid dated item returned by a successful provider page — paid data — is cached regardless of whether it falls inside the requested digest window, so a page fetched to cover one window never discards items outside it. Coverage rows record the exact inclusive requested periods (for example 13:00–19:00, both bounds inclusive) as a ledger distinct from item timestamps and from fetch progress: an item's date may lie anywhere in a fetched range, while coverage states only which requested periods were fully fetched. Ingestion asks the cache for uncovered gaps within the requested window and calls TwexAPI only for those gaps; overlapping or adjacent ranges merge into one covering row. Deduplication is by platform external ID. Fetch progress for ranges whose coverage is not yet committed lives in x_content_fetch_progress (migrations 0005 and 0006, cascade-deleted with their source): every successful provider page is durably recorded — items, the next cursor, a page count, and the page's cursor in a bounded history of the newest 500 — before another provider request, and coverage is committed only when the whole range is complete. A successful page, complete or incomplete, commits before an abort racing the response is propagated, so cancellation can never discard fetched items, cursors, or coverage; the next iteration's pre-request check still blocks further HTTP. Failed or interrupted runs therefore leave resumable state behind instead of re-fetching paid pages, and a later run whose window is already covered makes zero provider calls; the progress row is deleted when its range commits. Pending progress is resumed only when it intersects a required gap of the current window — pending ranges outside those gaps never force a provider call — and the required gaps are re-derived after each resumed range commits. X_CACHE_COVERAGE_TOLERANCE_MS (default 600000, 10 minutes; 0 disables) suppresses only small uncovered head/tail slivers of a requested window: a gap is skipped solely when it touches a window edge, is no wider than the tolerance, and real coverage exists inside the window; a wholly uncovered window and any internal gap are never suppressed. For example, with exact coverage 13:00–19:00 and a request for 12:50–19:10, both 10-minute edge slivers fall inside the tolerance, so the run makes zero provider calls and returns the cached messages. Suppressed gaps are not recorded as covered — stored ranges keep the exact inclusive requested periods — so the bounded risk is explicit: messages that fall only inside a tolerated edge sliver may be omitted by policy until a future request actually fetches that sliver. Safety limits are enforced against the durable page count before any further request: a chat range that records two incomplete all-mode pages fails locally on every later overlapping run, and a pending row whose terminal block reason — repeated_cursor (auto-detected from the durable cursor history inside the atomic page write, including cycles across restarts), missing_cursor (incomplete page without a resume cursor), or mismatched_conversation (a DM-history response for a different conversation than requested; fail-closed, no foreign messages cached, empty blocked page persisted) — intersects a required gap of the current window fails locally before any provider request. Terminal blocks are written atomically with the page that exposed them and are never cleared by later normal pages, so a blocked range can never be repurchased; the identity-less reconnect resets the X cache, subscriptions, and progress. Each cache instance is bound to the credential revision captured when the source snapshot was decrypted (see below), so operations from a stale in-flight handle reject rather than touch a reconnected source's data.
Account identity and reconnect semantics
Reconnecting with the same derived X user (the user info userId stored with the credentials) preserves the previously committed content cache, normalized items, and feed subscriptions, but still increments the credential revision and conservatively fences every older in-flight cache and ingestion handle. A changed, legacy (pre-cutover), disconnected, or undecryptable identity instead, inside the same immediate transaction, deletes the raw X cache (items, coverage ranges, and pending fetch progress), deletes the source's normalized items — including those of soft-deleted feeds, whose rows a later revival would reuse — clears the discovery catalog, soft-deletes the source's feeds, and only then stores the new encrypted credentials. The reconnect commit is a compare-and-swap: the source state captured before provider validation (same source id, credential revision, and connected flag) must still match inside the immediate transaction, so a concurrent disconnect or reconnect aborts with a fixed retry conflict instead of overwriting newer state. Disconnect itself is the generic credential removal: credentials are cleared, the source is disabled, its credential revision increments, active feeds are soft-deleted, and the catalog is revoked; previously captured content remains, and the identity-less reconnect after a disconnect takes the same full-reset path because no stored identity survives to be compared.
Credential revisions, stale in-flight fencing, and active-feed write guards
Migration 0003 adds sources.credential_revision, starting at 1 and incrementing on every credential replacement, reconnect, and disconnect. Each decrypted credential snapshot binds its content cache and connector handle to the captured revision. Fetch-planning reads — the missing-range and pending-progress lookups that decide whether the provider is called — preflight the source revision and the feed's active state (enabled, not soft-deleted) before any connector HTTP, so a stale or disabled feed cannot purchase paid pages; the raw cache read is source-revision-fenced only. Raw cache writes (the per-page progress write and the final coverage commit) are atomically source-revision plus active-feed guarded: they recheck the revision and the feed's active state inside the same immediate transaction, so they write nothing once the source was disconnected, disabled, or reconnected in the meantime. Normalized ingestion remains feed-fenced: every X ingestion mode carries the snapshot's sourceCredentialRevision, and the write transaction requires the source to still be connected and enabled at that revision and the feed still enabled and not soft-deleted before upserting items or advancing the feed watermark. The guard extends through digest generation: every contributing X feed's revision (recorded at ingestion or acceptance, including feeds skipped because they were already ingested) is re-asserted before item selection, immediately before and after every intelligence and summarizer await so no model-derived analysis, resolution, classification, or summary is persisted from a stale connection, immediately before the final story replacement commits, and once more before the digest is marked complete — a mismatch aborts the run. Beyond those boundary checks, a synchronous per-attempt assertion runs immediately before every outbound model HTTP request: each retry of a chat completion, semantic/member/split recovery retries, summarizer single/batch/vision and text-only-fallback calls, and each classification call. Revoked X content is therefore fenced before it can be sent to a model, not merely excluded from persisted output.
UI discovery-state invalidation
The Dashboard clears each source's discovered (availableFeeds) and loaded (sourceFeeds) state on disconnect, and clears the X source's state both before and after a reconnect — covering both a preserved source id and a newly created one — so a retained source id can never expose stale groups or lists and fresh discovery is required after any reconnect. Clearing bumps a per-source state version, and an in-flight loaded-feed refresh applies its response only when the captured version still matches and the state was not cleared in the meantime, so a late response resolving after a disconnect or reconnect cannot resurrect the cleared feeds.
Encrypted credentials and full-cookie boundary
The stored credential contains the API key, auth token, full cookie, optional PIN, list query, and the derived X user ID and username, envelope-encrypted with AES-256-GCM and owner-bound AAD. The full cookie is sent only to the TwexAPI base URL and only to the XChat endpoints; the auth token alone identifies the account at user info. Secrets are never returned by the API, never logged, and cleared from the web form on success.
Base URL precedence
The TwexAPI base URL resolves by explicit typed constructor argument, then TWEXAPI_BASE_URL, then the code default https://api.twexapi.io. The resolved value must be an absolute HTTPS URL without embedded credentials, query parameters, or fragments — any other value fails configuration visibly. Every request sends the API key as a bearer token and sets redirect: "error", so an HTTP downgrade or a redirecting endpoint is rejected rather than followed. A non-loopback provider means X session material leaves the host, which operators must include in their deployment policy.
Retention of captured X content
Raw cached X posts and chat messages—including captured disappearing messages—and their normalized item rows are retained until an account-identity reset removes those rows: disconnect preserves them, a same-account reconnect preserves committed content and subscriptions while fencing older handles, and only a reconnect to a changed or unknown identity deletes the raw cache and normalized items, clears the catalog, and soft-deletes the feeds. The connection reset is not a general erasure operation: already materialized stories, summaries, feedback, digest-derived content, and other downstream records remain governed by the application’s existing retention behavior. Capture overrides X disappearance: deleting or expiring content on X does not delete the retained Morning Post copies.
Roadmap: configurable retention
The remaining X roadmap is configurable cascading retention, not connector implementation. Retention must cascade through items, analyses, media, summaries, stories, story-feedback records, and digest-derived content, with complete deletion of captured X artifacts. No retention configuration key exists today.
Runtime and startup

Local startup pins the Bun toolchain, listener addresses, scheduler semantics, and frontend proxy path.

The backend runtime and workspace package manager require Bun 1.3.14; SQLite is built into Bun and needs no separate database service. Node.js 22.13+ remains a frontend and Playwright toolchain prerequisite because apps/web declares that engine; it is not the top-level package manager. bun install installs the root package and the apps/web workspace. Live and operational root scripts first run bun run env:check, then explicitly load the gitignored .env.production.local; startup therefore neither depends on implicit environment-file discovery nor proceeds with an incomplete operator configuration.

X operation requires outbound HTTPS to the TwexAPI base URL (default https://api.twexapi.io, override with TWEXAPI_BASE_URL); it needs no browser binary, profile directory, or display. Browser automation exists only in the ordinary web E2E suite (bun run web:e2e), which runs Playwright against the SPA, not against X.

The active database client is Bun 1.3.14 bun:sqlite, adapted by Drizzle bun-sqlite. It is synchronous: transactions execute immediately and transaction callbacks must not contain await. One connection serializes writes while WAL permits concurrent readers.

SQLite migration lifecycle: Fresh installs apply the ordered migration set; the additive story-detail migration also updates existing owner databases with the non-null Balanced default, migration 0002 adds the source-scoped X raw-item cache and inclusive coverage-range tables (x_content_cache_items, x_content_cache_ranges), migration 0003 adds the non-null sources.credential_revision column (default 1) that every credential replacement, reconnect, and disconnect increments, and migration 0004 adds the revision-bound discovery authorization catalog x_discovered_feeds (plaintext external IDs with canonical name/kind and a news | discussion check, unique per source, credential revision, and external ID, cascade-deleted with the source), and migrations 0005–0006 add and extend the per-range fetch-progress table x_content_fetch_progress (unique per source, feed external ID, and range; cascade-deleted with the source), which durably records each successful provider page before the next request so interrupted ranges resume from their saved cursor and safety limits are enforced against the durable page count; migration 0006 adds a bounded per-range cursor history (newest 500) and a terminal blocked_reason (repeated_cursor, missing_cursor, or mismatched_conversation) so cursor cycles and terminal provider states are persisted atomically with the page that exposed them and later overlapping runs fail locally instead of repurchasing. DATABASE_PATH selects the local file and defaults to ./data/morning-post.sqlite; opening the database creates its parent directory when needed. The database file and its -wal/-shm companions belong to one application host and must not be placed on network storage. Cleanup preserves the schema and migration history while deleting application rows; reset removes all three files and reapplies every migration.

Testing contract: ordinary bun run test invokes bun test tests directly: it neither validates nor loads the gitignored production environment. Unit tests receive configuration through typed constructor/dependency overrides and each database test callback receives a fresh in-memory SQLite database with the baseline applied and closes it afterward. File-backed and browser E2E setup and teardown remove the database plus -wal and -shm companions so state cannot leak between runs. Live analysis contract tests, browser E2E commands, API/CLI startup, and database operations are operational commands: they validate key parity first and explicitly load .env.production.local.

Current runtime: Hono is served by Bun.serve. Croner 10.0.1 schedules retained jobs in UTC with five-part expressions, rejects duplicate job names, uses protect: true to skip overlapping callbacks within the process, sanitizes and logs callback errors through its catch handler, and stops and clears every retained job when CronScheduler.stop() is called. API boot recovers stale digest runs before registering jobs. Every digest tick repeats stale-run recovery, selects the earliest user by (createdAt, id), and runs for that owner or returns without work when no owner exists.

The clean SQLite baseline contains no scheduler_leases table. Runtime leader election, user paging, bounded user concurrency, and SCHEDULER_LEASE_MS are absent because the supported deployment has one owner and one scheduler process. Croner callback protection prevents in-process overlap; it is not a distributed-scheduler claim.

Configuration boundary

Configuration is split by who owns the decision. The owner controls semantic behavior—summary breadth (maximumStoriesPerDigest), story detail (storyDetailLevel), relevance mode and threshold, prompts, rules, and per-feed relevance/detail overrides—through authenticated UI/API mutations persisted in SQLite. Low-level prompt packing, request-size limits, item and story batch sizes, output ceilings, and retry counts have typed, code-owned supported defaults rather than ordinary operator tuning. Their existing environment variables remain optional advanced escape hatches, listed only as comments in .env.example; each resolves by explicit constructor override, then environment, then the code default. Cache-version constants remain code-only. Tests clear process-global settings or use explicit constructor/dependency injection so a developer's local environment cannot redefine the unit-test contract.

The active operator environment is intentionally limited to deployment concerns represented by assignment lines in .env.example: listener/origin/proxy and request routing, database paths, remote-provider permission, provider credentials/model endpoints/pricing, connector and model timeouts, summary worker concurrency, TwexAPI base URL and X cache coverage tolerance, digest progress/stale-run handling, and media retention/quota. scripts/validate-env.ts compares assignment-key sets from .env.example and .env.production.local: comments—including the advanced budget examples—values, ordering, and extra production keys are irrelevant; only missing active example key names are sorted and reported, and values are never printed.

X connector configuration contract: the X deployment knobs are TWEXAPI_BASE_URL and X_CACHE_COVERAGE_TOLERANCE_MS. TWEXAPI_BASE_URL resolves by explicit typed constructor argument, then environment, then the code default https://api.twexapi.io; invalid values fail configuration visibly rather than being ignored. X_CACHE_COVERAGE_TOLERANCE_MS sets the cache-coverage edge tolerance (default 600000 ms, 10 minutes; 0 disables suppression) described in the cache-coverage entry above. There are no X_BROWSER_* settings, browser channels, profile roots, or login-timeout variables.

Domain model

The story model is connector-neutral and internally user-scoped around one supported owner.

Sources represent connector accounts and feeds represent subscriptions. Connector items are cached once, analyzed into common topics/entities/story and development keys, then linked into evolving user-owned stories. New digests persist selected story-version snapshots with every source; historical pre-story summaries remain read-only so old digests continue to render. Interest rules and feed/source policy overrides control zero-to-all relevance filtering. Feedback records the delivered digest/story/version identity and can update the same interest profile transactionally.

Semantic detail boundary: the owner's persisted storyDetailLevel is the baseline for every story: Headlines, Balanced, or Thorough. A feed's legacy-named summarizationMode is only an inheritance/opt-up switch: basic inherits the profile baseline, while thorough raises any story containing that feed's item to Thorough. Thorough therefore wins across mixed feeds and sources, but a basic feed never downgrades a Thorough profile. Channels and publications attached to the same source may opt up independently.

Owner identity and existing rows: users.email remains a unique internal compatibility column. Atomic first-run setup writes the non-routable sentinel owner@morning-post.invalid, the name displayed in digests, and a null password hash; email is never accepted by setup or login and is omitted from PublicUser. Existing password-backed owner rows retain password login compatibility.

One running digest per internal user is intentional; in the supported deployment, scheduled work targets only the owner. After a Dashboard reload, the initial run-status check restores any persisted running state and duplicate submission remains blocked until that check settles. While a run is active, the Dashboard polls its status every five seconds without overlapping requests and refreshes the digest list when the run reaches a terminal state. If POST /digests/run loses a race and returns 409, the Dashboard maps the conflict to the active-run UI instead of displaying raw error text.

Each digest-list row exposes when its latest linked run started and, when that run is terminal, its elapsed wall-clock time from digest_runs.started_at to finished_at. Digests without a linked run fall back to their own creation timestamp. The repository selects one run per listed digest with deterministic newest-first ordering, so pagination does not inflate the response with historical run rows.

API startup and every digest scheduler tick call recoverStaleDigestRuns(). On a tick, recovery completes before findOwner(); the callback then processes no user when the table is empty or exactly the earliest owner row. Recovery marks only runs older than DIGEST_RUN_STALE_AFTER_MS and their still-running feed stages as failed; terminal feed stages and fresh manual or scheduled runs remain unchanged. Croner protect: true prevents an overlapping tick in the same process, and the partial unique index on running userId remains the persistence guard against a duplicate active digest.

Digest archive ordering: createdAt records request order — the digest row is created when its run persists the period — so the archive defaults to newest-requested first. GET /digests accepts sort with exactly four modes: requested_desc (the default), requested_asc, period_desc, and period_asc; the period_* modes order by the digest's coverage periodEndMs instead of request time. Every ordering keys on the selected column first and then the stable digest id in the same direction, so equal sort values still page deterministically without skipping or repeating a row.

Archive cursors are bound to their sort. Each opaque base64url cursor encodes the sort it was minted under together with the period, request timestamp, and id of the last row; decoding validates the schema and rejects a cursor whose embedded sort differs from the request's sort with the standard validation error. A cursor can therefore never silently resume a page under a different ordering, and the web client clears its cursor whenever the archive sort changes. Limits remain default 20 and maximum 100, with { data, nextCursor } responses.

Reader route separation: the reader is a web presentation, not a second API surface. The SPA route /issues/:id renders a completed digest inside the AppShell by loading the same authenticated GET /digests/:id API DigestView, so it inherits the API's ownership scoping, projection, and optional markdown variant. /digests/:id remains the sole API DigestView route; /issues/:id adds no separate data path.

Digest media boundary: GET /digests/:digestId/items/:itemId/media is authenticated and ownership-scoped: the digest must belong to the session user and the item must be referenced by that digest's stories (searched in display order) before any file is resolved; otherwise the route returns not found. Connector-relative media paths resolve under the connector's media root with two containment gates — lexical resolution inside the root and symlink-resolved realpath still inside the realpath'd root — and only existing regular files with a known image content type are served. Responses set cache-control: private, no-store so an authorized response can never outlive the session that authorized it. The UI treats images as optional: story images load lazily through this endpoint and advance to the next image on error, so text remains the primary content and missing or failing media degrade the story card, not the digest.

Summary-point reuse is independent of repeat suppression. A profile change or feed opt-up therefore cannot reuse output from another detail policy; switching back may reuse the matching prior card only when the complete cache tuple still matches. Migrated pre-policy cards are legacy and miss once.

Story analysis is checkpointed independently of later resolution and summarization. Cache misses are grouped conservatively into discussion units: an explicit thread is split at eight members or a 30-minute gap, while rootless same-author group-chat adjacency is limited to four messages within two minutes. Each requested member still receives a distinct (unit, member) result, trusted URLs, evidence, and semantic fingerprint; one member can never inherit another member's output. Model batches contain at most 50 members and 50 transport records by default, are additionally bounded by an output-capacity estimate, and include UTF-8 newline framing within the configured 120 kB user-content budget. Long member text is capped at 16 kB; an oversized discussion unit is split into contiguous transport windows while retaining at least 2 kB per included member or rejected before a provider call. Missing or duplicate provider members retain unaffected valid results and retry only unresolved members; an unknown or unassignable record invalidates the whole response and retries every expected member. Each recovery request contains exactly one member under provider-local (0, 0) transport indexes, then maps the validated result back to its original pair. Recovery runs with at most three provider requests concurrently, still requires exactly one valid result per isolated request, and never synthesizes output or assigns one member's result to another. A second integrity violation fails with content-safe diagnostics covering response shape, unknown indexes, malformed schema fields, duplicate indexes, and unassignable record count. The opt-in bun run test:analysis:live contract test uses the configured ANALYSIS_MODEL, ANALYSIS_BASE_URL, and ANALYSIS_API_KEY path against independent, threaded, Unicode, JSON-like, and nullable-metadata inputs. A checkpoint is accepted only when it contains exactly one result for every requested item ID and current fingerprint, then persisted atomically.

Story-analysis model-output integrity: JSON-object mode requests one top-level object containing exactly a results array. Before coverage validation, the parser normalizes that canonical wrapper, a legacy top-level array, or—only when exactly one member is expected—a direct analysis record that satisfies the strict record schema. It does not accept arbitrary provider objects: a wrapper with fields other than results, a non-array results value, and any other object shape remain invalid non-array responses. After normalization, the same strict record-schema, exact (unit, member) coverage, unknown-index, duplicate-index, and malformed-record checks apply unchanged.

Story-analysis output-limit recovery: a provider response with finish_reason = length is an explicit output_limit failure, so any truncated content is discarded before parsing. When the pending analysis request covers multiple members, completion recursively bisects the expected member set into two nonempty halves, re-encodes each half's transport records with the existing record encoder, completes both smaller requests, and concatenates their results. The split is by member coverage rather than by original transport-record count, so it also recovers a single discussion record containing multiple members. Every recursive result must still satisfy the unchanged strict schema and exact (unit, member) coverage checks; if a singleton member still exhausts the output limit, that original error is terminal. This semantic bisection is reserved for ModelApiError instances of kind output_limit; unrelated provider, transport, parsing, and validation errors propagate without semantic retry. It is distinct from malformed-response isolation, which retries an individually malformed analysis member while preserving valid siblings, and from structured summary recovery, which makes one constrained same-input summary request rather than partitioning analysis coverage.

Analysis output is intentionally narrow: topics and entities are capped at five values, provider-supplied language, canonical URL, and media-description fields were removed, and each item may retain at most three verbatim evidence excerpts of at most 400 UTF-8 bytes. Extra, non-string, duplicate, or overlong evidence is discarded without failing otherwise valid member identity output; retained evidence must also be an exact substring of that member's source title or body. The repository independently enforces the same count and byte bounds. Low-text media invokes the vision path, while ordinary text-only items do not. Identical semantic item/media identities share successful or in-flight descriptions; title, body, source, and media differences receive distinct cache entries, and rejected promises are evicted so a later run can retry.

Vision output identity and coverage: each supplied image has the stable pair identity (i,m), where i is the item index and m is that item's one-based image number; the prompt labels every image with both values and requests a concise description of at most 40 words. JSON-object mode uses the canonical shape {"results":[{"i":0,"m":1,"description":"..."}]}. A legacy top-level array is accepted only when every element is the same strict three-field pair record. Wrapper extras, record extras, unknown or duplicate pairs, and any missing expected pair invalidate the entire vision result. After exact pair coverage is established, descriptions are aggregated per item in ascending image-number order and labeled Image N: ....

Optional vision failure semantics: live reproduction separated two request-contract defects from provider availability. A nine-image album using the former MEDIA_MAX_OUTPUT_TOKENS = 300 default ended with finish_reason = length; increasing the ceiling exposed the independent ambiguity of a single item index for multiple images, producing nine item indexes even though every image belonged to item 0. The explicit pair contract returned exact (0,1) through (0,9) coverage within the new 1200-token default. A truncated, malformed, or coverage-invalid vision response still emits an optional warning and falls back to text-only summarization; it does not by itself fail or terminate the digest. In contrast, failures in required analysis, classification, or terminal digest assembly follow their documented stage and persistence semantics.

Relevance-classification recovery: classification keeps a strict indexed-array contract, with two distinct recovery paths. For a completed, parseable response that stops before returning every candidate, valid rows are retained and only missing indexes are requested again with the same shared context and completion options (including timeout and telemetry). This malformed-result recovery is bounded by strict progress: a response that supplies some requested rows recurses only over the smaller missing set; a zero-row response for multiple candidates bisects that candidate set; and a singleton that is still omitted fails classification. Duplicate or unknown indexes, malformed rows, invalid scores, unknown matched-rule IDs, and invalid reason types fail immediately rather than entering missing-row recovery. At the provider boundary only, an observed null reason is normalized to the deterministic diagnostic No classification reason provided.; the otherwise valid score and classification result remain usable. Separately, a provider output_limit failure means the response may be truncated: its content is discarded without parsing or retaining any rows. A multi-story request batch is recursively bisected into two nonempty story halves and both halves are classified under the existing configured completion options; exhaustion for a singleton story is terminal and propagates the original output_limit error. All unrelated provider and application failures propagate unchanged. This story-batch split is classification-specific and differs from story-analysis recovery, which splits expected analysis-member coverage and re-encodes transport records. Every successful classification call still passes the unchanged strict row validation and missing-index recovery, and recovered decisions are reassembled in original story order with exactly one valid result for every original index. Thus partial provider output can trigger bounded completion calls, but truncated or incomplete digest classification is never accepted.

Final summarization filters reusable cards before model packing. Eligible text-only stories are compacted without mutating stored items and packed into typed requests of at most five stories and 120 kB; long items carry their title, grounded evidence, and bounded leading/trailing context. Strict story IDs bind every returned point to its input story and reject duplicate, missing, or unknown results. A failed or malformed batch member is retried once through the established isolated single-story summarization path under the same bounded worker concurrency. Exhausted failures retain an existing valid card when available. If some selected stories remain available, the digest is marked failed while the run is partial and persists the first sanitized summary reason; if every selected story lacks a usable summary, assembly and the run fail with that exact reason instead of the generic digest failure message. Stories with media or oversized payloads keep the established isolated chunk/merge path. Both batch and single calls run through the configured bounded summary worker pool.

Structured summary output-limit recovery: the OpenAI-compatible boundary treats a successful response whose first choice has finish_reason = length as a machine-readable output_limit failure even when message.content is nonempty. Truncated content is neither exposed nor parsed, and this failure is not blindly transport-retried. Single-story and recursive merge-summary completion perform exactly one semantic recovery request with the same input, original system prompt, SUMMARY_MAX_OUTPUT_TOKENS = 4000 cap, timeout, cancellation, telemetry, and transport-retry settings, but with the centrally defined constrained summary ruleset. That ruleset requires immediate valid JSON with no preamble, at most 12 points total, each point text at most 500 characters, dense consolidation of related grounded evidence, preservation of distinct material developments, and source attribution drawn only from the input. The recovery is therefore not an identical retry and does not raise or bypass the token cap. Same-model multimodal single-story summaries use this same recovery path. Batched summaries do not make this semantic recovery request directly: story-digest isolation already falls each failed batch member back to single-story summarization, where the one-shot recovery applies. If that constrained recovery also exhausts the output limit, summarization fails and the error propagates.

Cross-item story resolution no longer invokes fuzzy model adjudication. Membership is deterministic and conservative: exact normalized keys group current items first, then an exact trusted canonical URL may join current items, then an exact current story key may match a recent canonical story key; otherwise a new story is created. Stored non-story identifiers are deliberately excluded because they are story-qualified and suffix matching could merge unrelated stories. This removes the quadratic fuzzy-pair provider stage and its prompt amplification at the cost of leaving semantically similar but differently keyed items as separate stories.

Model metadata is normalized at the provider boundary without weakening index or provenance checks. If storyTitle is empty or omitted, the deterministic fallback order is the trimmed source title, then the normalized story key. Empty, omitted, or punctuation-only story/development identity fields no longer fail an otherwise complete analysis batch: the affected member receives item-ID-qualified story and development keys, deliberately isolating it instead of risking a false cross-item merge; valid siblings remain usable. Safe optional metadata omissions otherwise use conservative defaults: nullable language/media become null, topic/entity and evidence lists become empty, trusted canonical URLs come from normalized input, and absent development metadata derives from the fallback development key or source title. This tolerance still rejects missing indexes, unknown indexes, duplicate outputs, cross-member evidence, mismatched fingerprints, unknown fields, and malformed non-string metadata.

A failed digest view obtains its reason only from the newest run linked to that exact digest and owned by the requesting user. Newest-run lookup is deterministic: startedAt DESC, then finishedAt DESC NULLS LAST, then run id DESC. A newest failed or partial run with non-null error text contributes failureReason; this lets an exhausted isolated summary failure remain actionable even when other story cards survive. The text is sanitized again at projection time. The same owner-scoped value is returned in JSON, escaped in Markdown, shown as an alert in selected digest detail, and surfaced immediately by the runner when POST /digests/run returns the affected DigestView. Complete, reason-less, foreign-user, and merely period-overlapping runs do not expose a reason.

This distinguishes warning-level media enrichment loss from a terminal digest failure. Earlier persisted failures remain necessary regression evidence rather than superseded diagnoses: analysis integrity failures, incomplete classification recovery, and a classification-stage ECONNRESET each occurred at a distinct required stage and justify retaining their respective fixes. Current failure isolation

A connector creation or feed-ingestion failure is recorded on the affected run-feed row while successful feeds can still contribute. Story analysis or deterministic-resolution errors fail assembly; selected-story summary errors are isolated by bounded workers, mark the digest/run partial, and retain a prior valid card for that story when one exists. Security review

For an owner-operated self-host, process privilege, credential custody, plaintext provider boundaries, and edge hardening remain primary risks.

Supported v1 threat model: one primary owner administers one independent instance; there is no Morning Post-operated shared API, database, or credential vault. The operator is the custodian, not an absence of custody. Host or process compromise can expose credentials and locally decrypted plaintext, and configured remote summarization sends selected content beyond the host. Name-only setup and passwordless continuation make network reachability sufficient to obtain an owner session on a fresh deployment; keep the app on loopback or behind an operator-controlled authenticated reverse proxy, VPN, or equivalent boundary. Existing owners with retained hashes still receive Argon2id verification. Sessions, atomic setup and rate limits, userId ownership filters, credential encryption, protected backups, filesystem ACLs, updates, and host isolation remain required defense-in-depth.

Scalability review

The supported scale target is one owner's workload on one host; internal scoping and bounded pipeline work provide containment and predictable pressure.

The runtime is intentionally single-owner and single-process. Data remains userId-scoped and persistence operations remain idempotent. One SQLite connection serializes writers while WAL readers may proceed concurrently; this is the supported topology, not a distributed coordination claim. Multiple API writers, multiple hosts, network filesystems, sustained write contention, or a hosted multi-owner service require a future client/server database and an explicit coordination design.
